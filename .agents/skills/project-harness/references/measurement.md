# 度量与规模化

做度量、判断成熟度、或引入大改监督前读这份。

---

## 一、成熟度分级

用"agent 能自己做多少"来定位，不是打分。

| 级别 | 状态 | 人的角色 | 升级条件 |
|---|---|---|---|
| L0 | 人手点、人翻日志 | 全程手工 | 关键步骤有结构化事件 |
| L1 | 有事件，但人读 | 人读事件判断 | 判定写成可运行检查，且能红 |
| L2 | 人触发、机器判 | 人点，机器判 | 有程序化入口，走真人路径 |
| L3 | agent 自己触发、自己判 | 必要时介入 | 事件带层与来源；证据可按 session 聚合 |
| L4 | 全链自跑、跨服务对证据 | 看结论 | 失败可归因到可自动处理的范围 |
| L5 | 失败能自定位/自修 | 定方向 | 个例验证，不承诺泛化 |

### 关键判断

- **杠杆点在 L2 → L3。** L2 解决了"有没有判据"，L3 解决"谁来做调度"。大多数团队卡在 L2，因为触发入口需要改动产品代码，看起来成本高；但不做，验证永远要人陪。
- **L4 不是必选项。** 跨服务对证据的成本高，只在高风险链路上做。
- **L5 只当个例。** "保存冲突自动重试"这种自愈是苗头，不要据此承诺"AI 会自己修"。

### 定位方法

对每个模块问三个问题：

1. 能不能一条命令得到通过/失败？
2. 失败时能不能直接知道断在哪层？
3. agent 能不能不经过人就跑完？

三个都是"是"→ L3 以上；第 1 个是、后两个否 → L2；都没有 → L0/L1。

## 二、北极星指标

### 定义

北极星指标（North Star Metric）是**最能代表真实价值的单一指标**。它的作用是防止过程指标替代真实结果。

### 设计规则

1. **一个波次只认一个。** 多个北极星等于没有。
2. **必须能用命令检查。** 不能靠汇报、截图、主观判断。
3. **自己跑，不看执行者自报。** 执行者说完成不算。
4. **能被改坏。** 指标不变说明它没有区分能力。

### 结果指标 vs 过程指标

| 类型 | 例子 | 用途 | 风险 |
|---|---|---|---|
| 结果指标 | 目标路径通过率、端到端成功率、错误率下降 | 判断是否真的前进 | 采集成本高 |
| 过程指标 | 测试数量、文件搬迁数、任务完成数 | 诊断进度、发现阻塞 | 会被优化成好看的数字 |

过程指标可以用来诊断，不能用来宣布成功。

### Goodhart 定律

当一个指标变成目标，它就不再是好的度量。防御方式：

- 指标必须与业务结果绑定，而不是与动作绑定。
- 定期检查指标是否还能被"做样子"满足。
- 关键指标配一条反向检查（例如：声称通过，但证据缺失则判失败）。

## 三、监督角色

### 何时引入

只有同时满足才需要：

- 改动大到人无法逐波检查。
- 波次之间存在依赖，需要持续校正方向。
- 有明确的业务北极星可以命令检查。

日常小修不需要。引入监督会增加沟通成本。

### 职责边界

**做：**

- 持续回答"真正要的结果有没有往前走"。
- 消化细节，只把需要拍板的内容上浮。
- 为每一波绑定一个可命令检查的业务指标。
- 记录人拍过的板、错过的判断、下轮不要重犯的错。

**不做：**

- 不写业务代码，不动 git。
- 不替人做产品决策。
- 不追求把进度条推快。

### 硬规则

- 执行者自报完成不算，监督者**自己跑命令**才算。
- 产品决策必须由人拍板；实现细节由执行者决定。
- 不得把产品决策包装成"技术风险大"绕过。
- 同一判断来回改两次，说明没把相关代码看完，应停下来查，而不是继续猜。

### 对上级的沟通

用对方能理解的业务场景说话，不堆内部编号。对方说"没看懂"，这一轮就算失败——不是表达问题，是没想清楚。

### 记录格式

每个大改留一份总控，至少包含：

- 本轮北极星（可命令检查）。
- 人拍过的板（决策 + 理由）。
- 每波状态（指标值，不是"完成了"）。
- 错过/走偏的判断。
- 下轮禁止重复的错误。

## 四、文档与资产的生命周期

### 规模的双面性

文档是记忆层，但超过一定规模后，**发现成本会超过重写成本**：新人或 agent 找不到该看哪份，于是重新造一遍。

### 控制手段

1. **单一入口。** 所有资产的索引只放在一处（`AGENTS.md` 或入口文件）。
2. **命名可预测。** 用固定前缀/目录，便于扫描。
3. **一条路径一份文档。** 不要同一路径散在多处。
4. **索引优先于数量。** 当文档膨胀时，先补检索层（索引、`help()`、映射表），不要继续加文档。
5. **定期降级。** 三个月未引用的文档/技能，合并或删除。

### 验收文档的最小内容

1. 验的是哪条用户路径（不是哪个函数）。
2. 怎么触发。
3. 成功长什么样；没证据为何失败。
4. 证据在哪。
5. 哪些边界没验、为什么。
6. 下次怎么复跑。

缺少第 3 或第 6 项的文档，基本无法复用。

## 五、评审与节奏

| 周期 | 检查什么 | 产出 |
|---|---|---|
| 每次改动 | 相关检查是否通过、证据是否留下 | 验收记录 |
| 每周 | 新增/失效的路径、失败的判定 | 待办与修复 |
| 每月 | 规则/技能引用率、文档索引有效性 | 合并或删除清单 |
| 每季度 | 成熟度是否升级、北极星是否仍有效 | 下一阶段目标 |

不要用"文档数量""测试数量"作为季度成果。用"AI 能独立完成的验证路径数量"和"这些路径的失败率"。

## 六、反模式

| 反模式 | 表象 | 修正 |
|---|---|---|
| 多个北极星 | 每个波次都在追不同目标 | 收敛到一个可命令检查的指标 |
| 过程指标当结果 | 汇报全绿，业务没动 | 换结果指标，或加反向检查 |
| 监督者写代码 | 越权、失去独立判断 | 明确职责边界 |
| 监督者只收集汇报 | 指标很好看，方向偏了 | 自己跑命令 |
| 文档只增不减 | 索引失效、复用率下降 | 定期合并/删除 |
| 把 L5 当默认能力 | 对自愈能力过度承诺 | 只对个例陈述 |
| 用数量衡量健康度 | 数量增长但没人用 | 改看引用率与覆盖路径数 |
