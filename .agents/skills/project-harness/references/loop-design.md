# 回路设计

六个槽位的落地细节。设计探针、判定或触发入口前读这份。

---

## 1. 触发（执行器）

### 原则

程序化入口必须复用真人的处理路径。旁路一旦存在，就会有两条会漂移的路径：探针在假路上全绿，真实场景全红。这种虚假信心比直接报错更贵。

### 检查清单

- [ ] 入口调用的服务/函数与界面/CLI 调用的是同一个。
- [ ] 不跳过鉴权、校验、事务、中间件。
- [ ] 不直接写库来代替一次真实请求。
- [ ] 触发是幂等的，或能显式清理，便于复跑。
- [ ] 只在开发/测试环境生效，带环境守卫。
- [ ] 不重启他人正在使用的进程；需要时先探测端口与进程归属。

### 实现形态

| 形态 | 推荐做法 | 避免 |
|---|---|---|
| HTTP 服务 | 真实 HTTP 客户端 + 测试账号 + 固定 fixture | 直接调用内部 service 绕过路由 |
| Web 前端 | 浏览器自动化驱动真实控件 | 直接改 store / 调内部函数 |
| CLI | 真实二进制 + 参数 | 直接 import 内部模块 |
| 桌面端 | 驱动真实 UI 或 IPC 入口 | 直接调渲染层内部函数 |
| 数据管道 | 用真实输入跑一次完整 job | 只测单个算子 |

### 触发与判定解耦

触发通道和判定逻辑分别可运行：触发可以被替换（HTTP、CDP、CLI、队列），判定不应依赖触发方式，只依赖事件与终态。这样同一套判定能复用到不同入口，也能只换通道重跑。

---

## 2. 观测（传感器）

### 埋点位置

埋在最底层的共享层，一次覆盖所有上层。

| 技术栈 | 推荐层 | 理由 |
|---|---|---|
| 分层服务 | 中间件 / 拦截器 / 统一入口 | 所有路由共享 |
| 多端产品 | 共享核心包 | 各端继承 |
| 前端 | 网络层 + 状态变更层 | 覆盖交互与数据 |
| 数据管道 | 阶段/算子边界 | 覆盖全链 |
| 库/SDK | 核心执行路径 | 公开 API 都经过 |

不要在每个端点/页面各写一份：格式会分叉，新增路径会漏埋，维护成本线性增长。

### 事件 schema

一行一条 JSON，最小字段：

```json
{
  "ts": "2026-09-11T16:24:03.812Z",
  "session_id": "sess_01J8...",
  "layer": "domain|transport|storage|ui|job",
  "actor": "human|agent|system",
  "action": "document.save",
  "target": "doc_123",
  "result": "ok|error|skip",
  "duration_ms": 42,
  "error": {"code": "COLLAB_TIMEOUT", "message": "..."},
  "trace_id": "..."
}
```

要求：

- `session_id` 必须能贯穿一次用户操作的所有层，这是第 5 槽位一键取证的主键。
- `layer` 用固定枚举，不要自由文本。
- `actor` 区分人工与 agent，否则无法判断"是 AI 抄近道还是人点错了"。
- 失败事件必须有 `error.code`，不要只写 message。
- 单条事件自解释：只看这一条也能知道发生了什么。

### 不要记什么

- 不记录完整请求体、密码、个人信息。
- 不追求"记录一切"。记录判定需要的最小集合，其余给句柄。
- 大对象只记 ID 与摘要，需要时按 ID 回查。

## 3. 判定（比较器）

### 判定长什么样

一个判定由三部分组成：

1. **前置**：固定的输入与 fixture。
2. **期望**：事件序列（顺序、必须出现的、必须不出现的）或终态（返回值、数据库状态、文件内容）。
3. **失败条件**：缺任一必需证据即失败，而不是"没报错就通过"。

### 写法模式

```
给定 <输入>
当   <触发真实路径>
则   <终态断言>
并且 <必须出现的事件 A、B、C，且顺序正确>
并且 <不得出现事件 X>
```

### 硬要求

- **可证伪**：写完故意改坏实现，确认会红。不红就重写判定。
- **fail-closed**：证据缺失、超时、解析失败都判失败，不要 fail-open。
- **不依赖时序巧合**：用事件/轮询/显式等待，不用固定 sleep。
- **判定幂等**：连续跑两次结果一致。

### 选择断言层级

| 层级 | 适合 | 不适合 |
|---|---|---|
| 终态断言（值/行/文件） | 数据正确性 | 过程是否走对 |
| 事件序列断言 | 路径正确、层级定位 | 大范围业务正确性 |
| 跨服务对证据 | 端到端一致性 | 高频回归（成本高） |

优先终态 + 关键事件，不要堆满事件断言。断言越多越脆，维护成本会反噬。

---

## 4. 归因（定位）

目标是把"操作失败"变成"请求已发出，是协作层没有返回"。

### 分层约定

给项目定一套稳定的层名，所有事件必须落在枚举内。示例：

```
ui         用户/agent 动作
transport  HTTP/WS/RPC 接入与出站
domain     业务规则
storage    数据库/缓存/文件
job        异步任务
```

### 来源标记

- `actor=human`：真人操作。
- `actor=agent`：AI 触发。
- `actor=system`：定时任务、重试、补偿。

同一 session 里人工与 agent 的动作应能区分，否则无法判断问题来自哪一侧。

### 失败分类

| 类型 | 特征 | 排查方向 |
|---|---|---|
| 未触发 | 没有起始事件 | 入口、鉴权、开关 |
| 断在中途 | 有起始事件，无终止事件 | 该层超时、异常、死锁 |
| 结果不符 | 有完整事件，终态错 | 业务规则、数据、并发 |
| 多写/漏写 | 事件数量异常 | 重试、幂等、事务边界 |

新项目先把这四类跑通，通常能覆盖大部分排障场景。

## 5. 取证

### 证据映射表

维护一张"现象 → 去哪看"的表，放在固定位置：

| 现象 | 文件/命令 | 关键字段 |
|---|---|---|
| 请求失败 | 服务日志、访问日志 | `trace_id`、状态码 |
| 数据不一致 | 数据库查询、变更日志 | `session_id`、主键 |
| 异步未完成 | 任务队列/调度日志 | job id、重试次数 |
| 前端无响应 | 网络事件、控制台 | 请求 ID、错误栈 |

要求：新人或 agent 不问人，也能从现象查到位置。

### 一键捞取

提供按 `session_id` 聚合的证据命令：

```bash
scripts/evidence.sh <session_id>
```

至少聚合：应用事件、错误日志、相关数据库记录、任务状态。输出要能直接贴进对话，而不是让人再去找文件。

### 三方对照

验收时对齐三处：

1. 用户/调用方看到的（界面、返回值）。
2. 持久化记录的（数据库、文件）。
3. 系统自报的（事件、指标）。

三者一致才算通过；不一致本身就是最有价值的缺陷信号。

## 6. 登记

漏了这一步等于没做。下一个会话看不见，会重造一遍。

### 登记位置

优先复用项目已有的 agent 入口文件：

1. `AGENTS.md`
2. `CLAUDE.md`
3. `.cursor/rules/`
4. `.github/copilot-instructions.md`
5. 都没有 → 新建 `AGENTS.md`

不要同时维护两套，会分叉。

### 索引条目要写什么

- 这条验证覆盖哪条用户路径。
- 怎么跑（完整命令）。
- 成功/失败如何判断。
- 证据在哪。
- 文档与脚本的路径。

一条索引控制在几行，细节放验收文档里链接过去。

## 一次完整回路的样子

以 HTTP 服务为例：

```
触发：真实 HTTP 请求 → 路由 → 中间件（埋点）→ 领域服务 → 存储
事件：transport.request.start → domain.save.start → storage.write → domain.save.ok → transport.response
判定：终态 201 + 数据库存在记录 + 上述事件齐全且顺序正确
归因：若停在 domain.save.start，则是领域层阻塞；若停在 storage.write，则是存储层
取证：scripts/evidence.sh <session_id> 聚合日志与记录
登记：AGENTS.md 指向 docs/agent/acceptance/save-document.md
```

把这个骨架套到你的栈上，就是完整的一条回路。
