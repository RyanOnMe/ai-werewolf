# Project Harness

给仓库搭一套工程环境，使 AI 能在**不经过人转述**的情况下完成一次改动的验证：触发真实路径 → 看见发生了什么 → 判定对错 → 失败时定位到层 → 查到证据 → 把结论留给下一个会话。

产出不是"更多文档"，而是一条**能闭合的回路**。判断做没做完，只看一件事：AI 能不能自己点、自己看、自己判。

---

## 何时使用

适用：

- 项目会持续迭代数周以上，且会反复修改同一批路径。
- 每个新会话都要重新交代运行方式、复现步骤、日志位置、完成标准。
- 团队开始多人/多 agent 并行修改同一仓库。
- 已有测试，但没人能回答"这次改动到底过没过"。

不适用：

- 一次性脚本、一次性数据分析、寿命以天计的探索。
- 纯静态文档仓库，没有可执行行为可验证。
- 需求本身还没稳定到能定义"成功"。

对不适用的情况，不要搭全套。写一个能跑的验收脚本即可，等寿命和改动频率上来再升级。

---

## 核心模型

四条原理决定所有设计取舍：

1. **判定缺口（Oracle）**：agent 能行动，但不知道对错。必须把"成功长什么样"外化成可执行的检查，否则探针再多也只是日志。
2. **接口按 agent 设计（ACI）**：同样的能力，入口别扭就成功率骤降。给结构化、确定、可组合的入口，不要给"你自己去界面看看"。
3. **上下文经济学**：上下文窗口是稀缺资源。给**句柄**（路径、ID、查询接口），让 agent 按需取；不要一次性灌全量日志。
4. **可证伪性**：不会失败的检查不构成证据。每个判定都要有"别人改坏就会红"的场景。

人机分工的边界：**可写成"期望 X、实际 Y"的交给机器；"该不该做、好不好用"留给人。**

### 六槽位回路

| 槽位 | 作用 | 产出 | 缺了会怎样 |
|---|---|---|---|
| 1 触发 | 执行器 | 程序化入口，走真人同一路径 | 仍要人手点 |
| 2 观测 | 传感器 | 结构化事件流 | 只能截图/正则猜 |
| 3 判定 | 比较器 | 可运行的检查 | 有数据不知道过没过 |
| 4 归因 | 信号带层与来源 | 失败直接指到层 | 错误停在"操作失败" |
| 5 取证 | 现象→证据映射 | 对照表 + 一键捞取 | 靠老同事记忆 |
| 6 登记 | 发现与复用 | 索引条目 | 下个会话重造一遍 |

六个槽位是一个控制回路，不是并列清单。只做 1 和 3、跳过 2/4/5/6，会得到"能触发也能初判、但一失败就得喊人"的半成品。

## 流程

先跑审计，再决定投入。**不要**在没看清现状前直接写文档。

### Phase 0 — 现状勘察

1. 运行 `scripts/harness_audit.py --root <repo>`，得到五个支柱的覆盖情况。
2. 读项目现有的入口约定：`AGENTS.md` / `CLAUDE.md` / `.cursor/rules` / `README` / `Makefile` / `package.json` scripts / CI 配置。**沿用已有约定，不要另起一套。**
3. 确认项目形态（见下表），据此选真实入口和观测层。
4. 选**一条**人最常手工验证的用户路径。不要一次铺全仓库。

| 项目形态 | 真实入口 | 观测层（优先埋点位置） | 证据来源 |
|---|---|---|---|
| HTTP 服务 | 真实 HTTP 请求 | 中间件/拦截器（最底层共享层） | 请求日志、追踪、错误日志 |
| Web 前端 | 真实用户操作 | 网络层 + 状态层 | 网络事件、控制台、状态快照 |
| CLI | 真实命令 | 命令分发层 | 结构化 stdout/stderr、退出码 |
| 库 / SDK | 公开 API 调用 | 核心执行路径 | 调用日志、返回值断言 |
| 数据管道 | 一次完整 job | 算子/阶段边界 | 运行清单、行数与校验和 |
| 桌面端 | 真实 UI 动作 | IPC 桥或渲染/主进程边界 | 结构化事件日志、进程日志 |

**完成判据**：能用一句话说清"验的是用户哪条路径、起点在哪、成功长什么样"。说不清就回到第 4 步。

### Phase 1 — 先建传感器和判定（最高 ROI）

顺序很重要：先 2、3，再补 1。先有判据，触发才有意义。

1. 在**最底层的共享包/中间件**埋探针，不要每端各埋一份（会漂移、漏报、维护不动）。
2. 事件写成一行一条结构化记录，至少包含：`ts`、`session_id`、`layer`、`actor`（human/agent）、`action`、`target`、`result`、`duration_ms`、`error`。详细 schema 见 `references/loop-design.md`。
3. 写判定：给定输入 → 期望事件序列/终态 → 缺任何一环即失败。拒绝"没报错就算过"。
4. **验证检查会红**：故意制造一次失败，确认判定真的失败。不红就改判定。

**完成判据**：一条命令得到通过/失败；把实现改坏会让它变红。

### Phase 2 — 补触发入口

1. 提供程序化入口，但**必须复用真人的处理路径**。测试专用旁路会与真实路径漂移，制造虚假信心。
2. 触发后采集到的事件序列，应与手工操作的一致。不一致通常说明走了抄近道（如绕过 API 直接写库）。
3. 副作用工具只在开发环境生效；不要重启别人正在用的进程。

**完成判据**：AI 触发与人工触发产生同构的事件序列。

### Phase 3 — 归因与取证

1. 每个事件标注**层**（如接入/领域/存储/网络）和**来源**（人工/agent）。
2. 写"现象 → 看哪个日志/表/追踪"的对照表。
3. 提供按 `session_id` 一键捞齐相关证据的脚本或命令。
4. 验收时至少对三处：界面/返回值看到的、持久化记录、系统自报结果。

**完成判据**：一次失败无需人解释即可定位到层；新人或 agent 不问人就能从现象查到证据。

### Phase 4 — 登记与沉淀

1. 把入口、命令、路径写进项目已有的 agent 入口文件（`AGENTS.md` / `CLAUDE.md`，或扩展现有章节）。没有就新建 `AGENTS.md`。
2. 验收文档放到固定目录（如 `docs/agent/acceptance/`），能复跑的脚本放到 `scripts/`。
3. 文档必须写清：验的是哪条用户路径、怎么触发、成功长什么样、没证据为何失败、日志在哪、哪些边界没验、下次怎么复跑。
4. 只有同一类操作出现**三次以上**，才提升为 skill 或规则。过早抽象是维护负担。

**完成判据**：新的 agent 只读入口文件，就能发现并复跑这条验证。

### Phase 5 — 规模化（仅在确实需要时）

当改动大到人盯不住每一波时，才引入分波监督：

- 每一波只认**一个能用命令检查的业务结果**，执行者自报完成不算，监督者自己跑命令才算。
- 记录北极星指标、人拍过的板、每波状态、错过的判断。
- 产品决策必须由人拍板；实现细节由执行者决定。

规模不到不要做这一层。详见 `references/measurement.md`。

## 判定规则

**自动化 vs 留给人**

| 特征 | 处理 |
|---|---|
| 能写成"期望 X、实际 Y" | 交给机器 |
| 需要审美、手感、产品取舍 | 留给人 |
| 需要跨服务人工推理才能定位 | 先补归因，再谈自动化 |
| 只发生一次 | 不要工具化 |

**投入顺序**

1. 判定（第 3 槽位）> 观测 > 触发 > 归因 > 取证 > 登记。没有判定，其它都是成本。
2. 若已有成熟测试与 CI，从"把测试接到真实用户路径"开始，而不是重搭一套。
3. 若已有日志但没人用，先写判定和证据映射，不要加更多日志。

**成熟度定位**（用于决定下一步，而非评分）

| 级别 | 状态 | 下一步 |
|---|---|---|
| L0 | 人手点、人翻日志 | 先做结构化事件 + 判定 |
| L1 | 有事件，人读 | 把判定写成可运行检查 |
| L2 | 人触发、机器判 | 补程序化触发入口 |
| L3 | agent 自己触发、自己判 | 补归因与取证 |
| L4 | 全链自跑、跨服务对证据 | 补失败自愈（谨慎） |
| L5 | 失败能自定位/自修 | 个例验证，不要泛化承诺 |

杠杆点在 **L2 → L3**。L4/L5 依赖前级扎实。

## 输出契约

一次完整的 harness 建设应留下这些产物（按项目实际调整命名）：

| 产物 | 位置 | 作用 |
|---|---|---|
| 入口索引 | `AGENTS.md` 或已有入口文件 | 让下一个会话找到一切 |
| 回路说明 | `docs/agent/verification-loop.md` | 选了哪条路径、六个槽位怎么落 |
| 探针代码 | 最底层共享层 | 结构化事件 |
| 可跑检查 | `scripts/` 或测试目录 | 通过/失败 |
| 证据映射 | `docs/agent/evidence-map.md` | 现象→日志 |
| 捞取命令 | `scripts/` | 按 session 取证 |
| 验收文档 | `docs/agent/acceptance/` | 复跑步骤与边界 |

模板见 `references/templates.md`。

**不要**产出：为一次性场景写的规则、没有判定的探针、没人维护的文档目录、与现有约定重复的第二套入口文件。

## 反模式

| 反模式 | 表象 | 根因 | 对策 |
|---|---|---|---|
| 测试专用通道 | 探针全绿，真实场景失败 | 旁路与真路漂移 | 强制走真人同一路径 |
| 有探针无判据 | 数据很多，没人能说过没过 | 缺 oracle | 每个探针配一条可失败的检查 |
| 永不红的检查 | 测试永远绿 | 不可证伪 | 故意改坏一次验证 |
| 全量灌日志 | 上下文爆炸、信号被淹 | 违反上下文经济学 | 给句柄，按需取 |
| 每端各埋探针 | 漏报、格式不一 | 横切关注点放错层 | 埋最底层共享包 |
| 触发与判定耦死 | 换通道就要重写判定 | 未做关注点分离 | 两者独立可运行 |
| 报告式交付 | 汇报好看，业务没动 | Goodhart 定律 | 每波绑一个可命令检查的业务结果 |
| 抽象过早 | 大量一次性规则/技能 | 未达三次阈值 | 出现三次以上再抽象 |
| 临时目录沉淀 | 下个会话重做 | 未登记 | 验过即写入并登记 |
| 共享环境重置 | 并行时改动丢失 | 丢失更新竞态 | 分支动作推迟到提交时 |

**并行与共享环境**：多个写者共享一套有状态环境时，任何"为了干净而重置"的操作都可能抹掉别人的工作。切分支/清理工作区的动作，推迟到真正需要的时刻（提交），而不是习惯性的最早时刻。

## 完成检查

- [ ] 选定的路径能用一句话说明"验的是用户哪条路径"。
- [ ] AI 能不经人手触发这条路径。
- [ ] 关键步骤产出结构化事件，单条自解释。
- [ ] 一条命令给出通过/失败；改坏实现会变红。
- [ ] 失败能直接定位到层，不需要人推理。
- [ ] 现象能查到日志，有对照表和一键捞取。
- [ ] 入口文件里有这条验证的索引。
- [ ] 没有测试专用旁路。
- [ ] 没有为本可以留给人判断的事情造机器判据。
